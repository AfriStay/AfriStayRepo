AfriStay LTD — Storage Architecture

Supporting document for NCSA Application for Authorization to Store Personal Data Outside Rwanda
Document Reference: AfriStay-SA-001  |  Version 1.1  |  Prepared: 17 July 2026  |  Updated: 30 July 2026  |  Prepared by: Emmanuel BUTERA, CEO & Data Protection Officer, AfriStay LTD

1. Purpose

This document describes the technical architecture used by AfriStay LTD to store, process, and protect personal data collected through the AfriStay platform (https://afristay.rw), in support of AfriStay's application to the National Cyber Security Authority (NCSA) for authorization to store personal data outside Rwanda under Law N° 058/2021 of 13/10/2021.

2. High-Level Architecture

The AfriStay platform is a web application (static front-end pages served from web hosting in Rwanda) that communicates over HTTPS with a managed backend-as-a-service platform, Supabase, which provides the application database, user authentication, file storage, and serverless business-logic functions. A third-party service, Resend, is used solely to deliver transactional emails (e.g. booking confirmations). Payments are handled entirely by IremboPay, an independent, PCI-compliant Rwandan payment platform; AfriStay does not collect, transmit, or store any payment card or mobile money credentials.

3. Database Platform

AfriStay's core datastore is a managed PostgreSQL database provisioned through Supabase, hosted in Ireland (European Union). As of this document's preparation date, the database contains 34 application tables covering user accounts, listings, bookings, payments, reviews, notifications, and administrative logs. Every table has Row Level Security (RLS) enabled, meaning access to each row is enforced at the database level according to the requesting user's identity and role — a guest cannot read another guest's data, and an owner cannot read another owner's listings or bookings, regardless of what the front-end application requests.

5. Business Logic and Automation

The booking lifecycle (submission, owner approval/rejection, payment, confirmation, expiry, cancellation) is enforced primarily inside the database itself, through PL/pgSQL functions and triggers (65 functions and 39 triggers as of this document's revision date) — for example, automatic prevention of double-bookings, generation of secure booking-approval tokens, synchronisation of booking status after payment confirmation, automated encryption of sensitive payout fields prior to storage, and automated audit-log recording of changes to sensitive tables. Nine scheduled jobs (pg_cron) run at intervals between 5 minutes and daily to expire stale bookings, release listing availability, and enforce the data retention policy (see Section 7) automatically.

Sensitive operations (payment invoice creation, booking approval, account deletion, admin actions) are handled by 19 serverless "Edge Functions" running in an isolated Deno runtime. These functions hold the only credentials capable of bypassing row-level security (the Supabase "service role" key), and that key is never exposed to the front-end or to end users' browsers.

6. File Storage

Listing photos, listing videos, event images, and promotional images are stored in four Supabase Storage buckets. These buckets contain property/marketing media uploaded by Owners and platform administrators; they do not contain personal documents (e.g. ID scans) as AfriStay does not collect these.

7. Security Measures

  • Encryption in transit: all communication between the AfriStay front-end, Supabase, and Resend is encrypted via HTTPS/TLS.
  • Encryption at rest: the underlying database is stored using Supabase-managed encryption at rest (per Supabase's published infrastructure documentation).
  • Field-level encryption: sensitive payout fields (bank account numbers, mobile money numbers, account holder names) are additionally encrypted at the application/database layer using symmetric encryption before being written to disk, independent of the underlying infrastructure encryption. The encryption key is held in a dedicated secrets vault, never in application source code.
  • Access control: Row Level Security on every table; a public/anonymous API key restricted by RLS is used by the website, while the unrestricted service-role key is confined to server-side Edge Functions only.
  • Authentication: Supabase Auth manages user sign-up/sign-in with hashed credentials; AfriStay never stores plaintext passwords.
  • Administrative access control: administrative dashboard access requires standard password authentication and mandatory two-factor authentication (TOTP) for full access; accounts that have not yet activated two-factor authentication are gated by an individually-assigned fallback PIN, used only until two-factor authentication is enabled.
  • Webhook integrity: payment-status webhooks from IremboPay are verified using HMAC-SHA256 signature validation before any booking is marked as paid.
  • Audit logging: every create, update, and delete action on sensitive tables (user profiles, payout wallets, payments, bookings) is automatically recorded via database triggers, capturing the acting user, their role, and a before/after snapshot of the affected record.
  • Automated data retention enforcement: accounts marked for deletion have their personal data automatically anonymised after a 30-day retention window via a scheduled job, rather than relying on manual action.
  • Periodic access review: a dedicated internal function allows AfriStay's Data Protection Officer to review all administrator accounts, flagging dormant (90+ day inactive) or unrecognised accounts for review.
  • Backups: automated backups are maintained by Supabase according to AfriStay's subscription plan.
  • Vendor compliance: Supabase publishes independent security compliance reports (including SOC 2 Type II) via its public trust portal; AfriStay maintains a Data Processing Agreement with each infrastructure provider (see accompanying Data Flow Diagram & Sub-Processor Register).

7a. Incident Response

AfriStay maintains a written Data Breach Response and Notification Procedure (AfriStay-DBRP-001) defining containment, assessment, notification (to affected data subjects and the NCSA where applicable), and post-incident review steps in the event of a security incident, consistent with Law N° 058/2021.

8. Data Subject Rights

Because all personal data resides in a single managed database, AfriStay's Data Protection Officer can directly query, export, correct, or permanently delete any individual's records on request, consistent with AfriStay's Data Protection Commitments (AfriStay-DPC-001) and Privacy Policy, and can action deletions at the underlying infrastructure level with Supabase and Resend where required.
